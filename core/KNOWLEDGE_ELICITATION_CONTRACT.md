# Knowledge Elicitation State Machine Contract

This document is the authoritative contract for the schema-1, in-memory tacit-knowledge intake engine in `hooks/scripts/lib/knowledge-elicitation.mjs`. Persistence, CLI behavior, prompts, and Claude/Codex host integration are intentionally outside this contract.

## Purity and return values

Every public transition is a deterministic transform. It performs no file, process, network, clock, random, persistence, or host-adapter operation. A transition never mutates, freezes, or aliases caller-owned state or payloads. Successful state results are detached, recursively frozen JSON-safe projections. Failed transitions leave all inputs unchanged.

`createIntake`, mutation transitions, and terminal transitions return a state. `issueNextBatch` returns `{ state, questions }`; redelivery returns detached projections with byte-equivalent state and does not append history or charge issuance again.

All states have `schema: 1`. Every history event has `seq`, `id`, `type`, `questionId`, `supersedes[]`, and `payload`. Every knowledge record has `id`, `kind`, `value`, `provenance`, `conflictsWith[]`, and `supersedes[]`. IDs are unique across caller and engine records. Engine IDs are deterministic and collision-avoiding.

Inputs must consist only of finite numbers, strings, booleans, nulls, dense arrays, and enumerable data properties on plain objects. Cycles, `undefined`, functions, symbols, accessors, non-finite numbers, sparse arrays, and class instances are rejected as `INTAKE_NOT_JSON_SAFE`.

## Policy

`DEFAULT_INTAKE_POLICY` is frozen and defines hard maxima:

| Limit | Value | Accounting rule |
| --- | ---: | --- |
| Base questions | 30 | A canonical inventory contains at most 30 base questions. |
| Active follow-ups per base parent | 3 | A replacement set contains at most 3 active versions. |
| Allocated follow-ups | 12 | Every old and replacement allocation is charged permanently. |
| Issued question versions | 42 | First issue charges once; redelivery does not; invalidation never refunds. |
| Batch size | 3 | Active follow-ups precede base questions. |
| Re-baselines | 1 | A second request or accept path requires a split. |
| Synthesis corrections | 2 | The third attempt blocks. |
| Answer corrections | 6 | The seventh attempt blocks. |
| Successful resume cycles | 10 | Ten resumes succeed; the following pause attempt blocks. |

A caller may lower a policy value for bounded tests or a stricter embedding, but cannot raise a hard maximum or add policy fields.

## States and legal mutations

| Status | Legal mutations | Destinations |
| --- | --- | --- |
| `draft` | creation is represented by `createIntake`, not an input-state transition | `questioning`, or `awaiting-confirmation` for an empty inventory |
| `questioning` | issue, answer, skip, correct answer, pause, stop, request re-baseline, synthesize | `questioning`, `paused`, `awaiting-rebaseline`, `awaiting-confirmation`, `blocked`, `split-required` |
| `paused` | resume, stop | `questioning`, `blocked` |
| `awaiting-rebaseline` | accept/decline re-baseline, stop | `questioning`, `awaiting-confirmation`, `blocked`, `split-required` |
| `awaiting-confirmation` | correct synthesis, confirm, stop | `awaiting-confirmation`, `awaiting-rebaseline`, `confirmed`, `blocked`, `split-required` |
| `confirmed`, `blocked`, `split-required` | none | absorbing terminal |

An action from another nonterminal status throws `INTAKE_INVALID_TRANSITION`. Every action from a terminal status throws `INTAKE_TERMINAL`. Read-only inspection is outside the mutation matrix. Redelivery by `issueNextBatch` is explicitly non-mutating.

`stopIntake` is legal from `questioning`, `paused`, `awaiting-rebaseline`, and `awaiting-confirmation`. It appends `intake-stopped` and terminates as `blocked` with reason `BLOCKED_BY_USER`.

## Questions, labels, and accounting

A base inventory is canonical input order with contiguous ordinals `1..N`. A base question has no `parentId`. Its stable label is `[ordinal/baseTotal]`, for example `[17/30]`. Empty intake transitions directly to `awaiting-confirmation` and never constructs `[0/0]`.

Follow-up ordinals are generated by the engine as `1..N` for each active set and only a base question may be their parent. Labels use the base parent's ordinal and the replacement set's own total, for example `[17-1/3]`. Correcting a parent invalidates its entire pending/issued active follow-up set. The engine emits one `followup-invalidated` event per predecessor with the predecessor event in `supersedes[]` and the old label in payload. Replacement allocation events causally supersede that invalidated set. Old questions and events remain in history.

Issuance selects active follow-ups first, then base inventory order, up to the batch limit. The first issue changes `pending` to `issued`, increments `issuedVersions`, and appends `question-issued`. If issued unanswered questions already exist, the same versions and labels are redelivered without mutation. An attempted issue above the cumulative ceiling transitions to `split-required` with `ISSUED_VERSION_LIMIT`.

Question statuses are `pending`, `issued`, `answered`, `skipped`, `invalidated`, and `superseded`. Resolved, invalidated, and superseded versions are never selected for issuance.

## Materiality and knowledge

The material dimensions are `scope`, `acceptance`, `irreversible`, `risk`, `constraint`, and `external-integration`. They are material regardless of caller flags. Unknown, missing, or malformed dimensions are material by fail-closed rule.

The only potentially non-material dimensions are `preference`, `presentation`, `naming`, and `reversible-default`. Such a question is non-material only when `material:false` and `reversible:true` are both explicit. Skipping any other issued question blocks with `MATERIAL_QUESTION_SKIPPED`. Skipping an explicit reversible non-material question resolves it as typed `assumption` knowledge.

Knowledge kinds are `source-fact`, `user-decision`, `preference`, `constraint`, `assumption`, `open-question`, and `superseded`. Answer knowledge records preserve the supplied JSON-safe value and provenance plus their question/event provenance. `conflictsWith[]` can reference existing `source-fact` IDs only; both the source record and conflicting answer remain present.

Answer correction preserves the predecessor record by changing its projection kind to `superseded`, creates a replacement with `supersedes:[predecessorId]`, and causally links the correction event to the predecessor answer event. Correction does not refund issuance or follow-up allocations.

## Re-baseline, synthesis, and termination

`requestRebaseline` moves `questioning` to `awaiting-rebaseline`. Decline blocks with `REBASELINE_DECLINED`. Accept invalidates unresolved old versions while retaining all resolved knowledge and cumulative counters. It appends the old and new base totals, and installs a new canonical inventory whose IDs have never appeared before. A base overflow, a second re-baseline, or `issuedVersions + newInventory.length > issuedVersionLimit` transitions to `split-required`.

`synthesizeIntake` is legal only when no material question remains pending or issued. It records a JSON-safe synthesis and moves to `awaiting-confirmation`. A non-material synthesis correction replaces the synthesis in place. A material synthesis correction consumes a correction and uses the one remaining re-baseline path; if none remains, it requires a split. The third synthesis-correction attempt blocks. `confirmIntake` appends confirmation and enters the absorbing `confirmed` status.

Liveness is conditional on fair caller choice: in `questioning`, callers eventually answer, skip, stop, request re-baseline, or synthesize; in `paused`, resume or stop; in `awaiting-rebaseline`, accept, decline, or stop; and in `awaiting-confirmation`, correct, confirm, or stop. Read-only status calls and unanswered redelivery are not liveness mutations. All mutating cycles are bounded by the policy above.

A replacement session may explicitly claim a non-terminal intake with
`qe-intake claim` only when it supplies the exact previous owner UUID and current
revision. The transfer consumes one revision and records `ownershipHistory`;
stale owner, stale revision, same-owner, and terminal transfers fail closed.

## Stable error codes and terminal reasons

Thrown validation/transition codes are part of the public API:

- `INTAKE_INVALID_STATE`, `INTAKE_INVALID_TRANSITION`, `INTAKE_TERMINAL`
- `INTAKE_NOT_JSON_SAFE`, `INTAKE_INVALID_POLICY`, `INTAKE_INVALID_INVENTORY`, `INTAKE_INVALID_QUESTION`, `INTAKE_INVALID_ID`, `INTAKE_DUPLICATE_ID`
- `INTAKE_BASE_LIMIT`, `INTAKE_FOLLOWUP_PARENT_LIMIT`, `INTAKE_FOLLOWUP_ALLOCATION_LIMIT`
- `INTAKE_UNKNOWN_QUESTION`, `INTAKE_QUESTION_NOT_ISSUED`, `INTAKE_INVALID_ANSWER`, `INTAKE_INVALID_CORRECTION`
- `INTAKE_INVALID_SOURCE_FACT`, `INTAKE_INVALID_KNOWLEDGE`, `INTAKE_UNKNOWN_SOURCE_CONFLICT`
- `INTAKE_INVALID_REBASELINE`, `INTAKE_MATERIAL_UNRESOLVED`, `INTAKE_INVALID_SYNTHESIS`

Terminal reason values are also stable: `CONFIRMED`, `BLOCKED_BY_USER`, `MATERIAL_QUESTION_SKIPPED`, `ANSWER_CORRECTION_LIMIT`, `PAUSE_RESUME_LIMIT`, `REBASELINE_DECLINED`, `SYNTHESIS_CORRECTION_LIMIT`, `ISSUED_VERSION_LIMIT`, `REBASELINE_LIMIT`, `REBASELINE_BASE_LIMIT`, and `REBASELINE_POTENTIAL_LIMIT`.
