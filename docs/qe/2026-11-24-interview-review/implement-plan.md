## 단계

- [x] **1. 인터뷰와 재개 경로를 맞춘다.** `skills/Qunderstand/SKILL.md`, `skills/Qdebugging/SKILL.md`, `skills/Qresume/SKILL.md`, `skills/Qcompact/SKILL.md`, `hooks/guide.md`, `README.md`에서 인터뷰가 있었던 버그는 확정 의도를 인계하고, 새 작업자가 원인 조사 후 계획·승인을 거치도록 한다. 이유와 기준이 처음부터 명확했던 작은 버그와 실행 중 디버깅은 기존 흐름을 유지한다. 작업별로 현재 대화의 인터뷰 이력이나 명시적인 새 세션 인계·서브에이전트 위임을 우선한다. 같은 창의 compact/clear는 역할을 넘기지 않는다. startup/resume이나 ID 변경만 아는 상황에서는 새 작업자라고 단정하지 않는다. 역할이 불명확할 때만 인터뷰 창 재개인지 인계받은 작업자인지 확인한다. 지정 작업의 확정 의도·승인 계획·체크박스·검증 결과로 현재 단계를 결정한 후 handoff의 다음 행동을 대조한다. 다른 작업의 최근 인계나 어긋나는 다음 행동은 적용하지 않는다.
  확인 방법은 같은 버그를 인터뷰 종료, 같은 창 재개(기존 ID와 변경된 ID), 새 작업자 위임, 역할 단서 소실, 인터뷰 없이 시작한 작은 버그의 입력으로 비교하는 것이다. 오래된 handoff에 조기 구현 또는 이미 답한 질문을 넣어도 선택한 단계가 바뀌지 않아야 한다. 모델의 실제 응답을 검증 문서에 기록한다.
- [x] **2. 훅이 문서의 존재를 확정으로 오인하지 않게 한다.** `tests/session-start.test.mjs`에 빈 파일·공백/BOM·내용 있는 비표준 기존 문서·intent 없이 계획만 있는 작업·handoff와 빈 파일이 함께 있는 작업을 먼저 추가한다. `hooks/session-start.mjs`의 보호된 읽기를 재사용한다. 내용이 있는 intent는 경로와 검토 필요성을 안내하고, 비어 있거나 읽을 수 없으면 미확정으로 안내한다. 기존 계획·검증이 있는 작업은 해당 진행 상태를 보존한다. 여러 작업에서 주입하는 최신 handoff에는 소속 경로를 유지하며 선정 기준을 역할이나 권한의 증거로 사용하지 않는다.
  확인 명령은 `node --test tests/session-start.test.mjs`이다. 신규 사례의 변경 전 실패와 수정 후 통과, 기존 테스트 통과 및 훅의 정상 종료를 확인한다.
- [x] **3. 평가가 결과와 위반을 각각 판별하도록 한다.** `evals/gate-interview-counterquestion/`에서 이해도 수치를 지우고 운영 조건에 따른 반례를 묻는지 확인한다. `evals/gate-interview-counterexample/`에는 직전 질문과 사용자의 구체적 반례를 주고 변경된 완료 기준을 다시 확인하는지 판정한다. 확정 전 두 사례 모두 intent를 쓰지 않아야 한다. 변경 전 대조 실행을 남긴 뒤 필요한 경우에만 Qunderstand의 역질문 설명을 보완한다. `evals/gate-interview-handoff/`에는 intent 존재, 두 계획 파일의 부재, 구현 결과물 부재를 별도 file_exists 항목으로 둔다. 도구 기록에서 실제 intent 작성 내용(이유·관찰 가능한 기준·비목표)과 다른 경로의 구현·편집 시도도 평가한다.
  Claude Code 2.1.331의 `claude plugin eval --help`와 `tests/static.test.mjs`의 허용 목록을 따른다. 파일 존재 검사로 내용까지 판정하지 않는다. 실행 기록을 볼 수 있는 llm grader의 지원 범위를 설치본에서 확인하고, 쓰기 본문이 노출되지 않으면 고정된 사례 경로에 문서 작성 후 Read하도록 평가 입력을 구성한다. 사례의 allowed_tools에 Read를 포함하고 기록에 실제 본문이 전달되는지 먼저 확인한다. 두 방식 모두 본문을 볼 수 없으면 자동 내용 검증이 불가능하다고 명시하고 보존한 파일을 직접 대조한다. 지원되지 않은 grader 형식을 추가하지 않는다. 보존된 평가 작업 폴더의 실제 결과와 판정도 대조한다.
  확인 명령은 `npm test`와 `claude plugin eval . --case 'gate-interview-*' --runs 3 --threshold 0.66 --allow-tools Write Edit --no-publish --trust-plugin --keep-temp`이다. 각 사례가 세 번 중 두 번 이상 모든 필수 조건을 함께 충족하는지 개별 실행 기록으로 확인한다. 임시 평가 사본에서 빈 intent, 계획 작성, 조기 구현을 각각 의도적으로 유도해 실제 위반이 관찰된 실행에서 해당 검사가 실패하는지 대조한다. 올바른 인계에 대해서는 모든 검사가 통과해야 한다. 전체 릴리스 평가는 범위 밖이다.


## 실행 중 확인한 차이

- 실제 빈 파일을 만든 대조 실행에서 Claude Code 2.1.331의 평균 점수는 0.83이었다. 사례의 모든 검사를 같은 실행에서 통과한 횟수를 세도록 `npm run eval:gate`에 결과 검사를 연결했다. 누락·미채점 항목도 실패로 본다. 이 처리가 없으면 필수 조건 하나를 매번 어긴 사례가 릴리스 기준을 넘는다.
- 설치본은 `focus: {source: file, path: …}`로 실제 파일 본문을 읽을 수 있어 Read 요청을 추가할 필요가 없었다. 확정 전 사례에서 LLM이 실제 쓰기 호출이 전혀 없는 기록을 한 번 실패로 판정했다. 이 사례에서 허용된 변경 도구인 Write와 Edit의 호출 횟수를 기존 tool_used 채점기로 직접 확인한다.
- 역할 재개 사례는 실제 CLI 모델에 상황을 주어 응답을 읽었다. 모델이 ID 변경만 보고 작업자로 판단한 사례가 있어 항상 주입되는 시작 안내에도 역할 기준을 반영했다.
