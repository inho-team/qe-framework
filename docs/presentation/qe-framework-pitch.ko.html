01 · 출발점

왜 GUI 챗이 아니라 Claude CLI인가

자동화·계측이 가능한 "표면"이 있느냐의 차이입니다.

9개 라이프사이클 훅

SessionStart·PreToolUse·PostToolUse·PreCompact·Stop·UserPromptSubmit· Notification·TeammateIdle·TaskCompleted — 매 단계에 코드를 끼워 넣을 수 있다.

플러그인 표면

스킬·에이전트·MCP를 정식 플러그인으로 확장. 워크플로우가 재사용·버전관리된다.

모델 라우팅

단계별로 Opus/Sonnet/Haiku, 필요 시 Codex까지 라우팅. 비용·정확도를 설계한다.

GUI 챗에는 이 훅·플러그인·라우팅 표면이 없습니다. 터미널 CLI라서 비로소 "사람의 개입 없이도 매 단계가 강제·기록되는" 하네스를 얹을 수 있습니다.

근거: core/PHILOSOPHY.md (9 Hook Lifecycle Events), README.md
2 / 8
핵심 메시지: 우리가 CLI를 고른 건 취향이 아니라 "끼워 넣을 자리(훅)"가 있기 때문. 9개 훅은 PHILOSOPHY.md에 명시된 사실. "GUI엔 이 표면이 없다"는 부분은 근거: 추론 (CLI 플러그인 훅 표면의 존재로부터 도출). 상급자가 "ChatGPT 창에서 하면 안 되나?"라고 물으면 → "매 단계 자동 검증·기록·모델 라우팅을 걸 자리가 없습니다"가 답.
02 · 문제 정의

raw AI는 네 지점에서 무너진다

① No Spec

AI가 추측한다 → 사용자는 예상 밖 결과를 받는다.

② No Implementation Discipline

코드 변경과 검증이 뒤섞여, 무엇을 했고 무엇을 확인했는지 불분명.

③ No Verification

AI가 "끝났다"고 말한다. 아무도 확인하지 않는다. 버그가 출시된다.

④ No Supervision

로컬 체크는 통과하지만 실제 환경에서 실패한다.

스펙 없는 작업은 추측이고, 구현 없는 스펙은 의도일 뿐이며,
검증 없는 구현은 희망이고, 감독 없는 검증은 확증편향이다. — 핵심 원칙
근거: core/PHILOSOPHY.md ("Why This Matters", "The Core Principle")
3 / 8
이 네 가지는 PHILOSOPHY.md "Why This Matters"에 그대로 있는 사실. "프롬프트를 잘 쓰면 되지 않냐"는 반론에 대한 답: 매번 그 정밀도를 유지하는 게 사람에겐 지치는 일이다(README의 문제 정의). 프레임워크는 그 피로를 구조로 흡수한다. 다음 장에서 "그럼 어떻게 막느냐"로 자연스럽게 넘어갑니다.

03 · 어떻게 — 하네스 엔지니어링

왜 이렇게까지 하네스를 짜는가

Efficiency is Accuracy. — 컨텍스트 제약 환경에서 불필요한 토큰 하나가 곧 드리프트의 원인이다.

독립 검증 게이트

한 단계는 자기 출력을 스스로 인증할 수 없다(self-reference 문제). fresh-context 적대적 sub-agent가 별도로 검증한다.

모델 티어링

전략=Opus · 구현=Sonnet · 병렬작업=Haiku. 단계 난도에 맞춰 비용·속도를 배분.

폴더 인지 컨텍스트 메모리

작업 디렉터리에 매칭되는 컨텍스트만 로드(root + glob). 무관한 토큰을 안 싣는다.

9개 훅 + 토큰 효율 계층

중복 읽기 차단, 140k 자동·170k 강제 압축, 250줄 스킬 캡 — 매 단계가 자동 강제된다.

근거: core/PHILOSOPHY.md (Efficiency, Obligation #8), docs/SYSTEM_OVERVIEW.md
5 / 8
하네스 엔지니어링 = "AI를 어떻게 잘 묶어두느냐"의 공학. 핵심 논리: 효율은 비용 절감이 아니라 신뢰성 요건이다(토큰=드리프트). 독립 검증 게이트는 가장 설득력 있는 포인트 — "같은 모델이 자기 답을 채점하면 같은 맹점을 공유한다"를 강조. 모델 티어링은 비용 질문에 대한 선제 답변(전부 Opus로 안 돌린다).
04 · 이점

주관이 아니라 6개 정량 메트릭으로 본다

메트릭의미정상 범위경고 임계
Task Resolution Rate작업 완료율85–100%<70%
Pass@1 Rate첫 시도 전체 통과율60–80%<40%
Defect Escape Rate검증 통과 후 재수정률0–5%>15%
Code Churn Rate작업당 변경 라인(낮을수록 ↑)50–200 라인>500 라인
Verification Tax검증/구현 시간비0.1–0.5>1.0
Harness Constraint Effect훅 on/off 품질차+10–30%음수

"좋아 보인다"가 아니라 측정값으로 말합니다. 메트릭이 경고 임계를 넘으면 스펙 품질·검증 강도를 어디서 손봐야 하는지 곧장 지목됩니다.

근거: core/METRICS_SPEC.md (6 Harness Engineering Metrics)
6 / 8
이 장이 상급자 설득의 정점. 모든 수치는 METRICS_SPEC.md와 일치(확인함). 포인트: 프레임워크의 효과를 "느낌"이 아니라 숫자로 추적한다. 특히 Harness Constraint Effect(+10~30%)는 "훅을 켜면 품질이 실제로 오른다"는 A/B 측정. Verification Tax는 "검증이 과하지 않은지"를 스스로 감시하는 장치 — 즉 우리는 비용도 계측한다.
04 · 솔직한 평가

장점 vs 단점

장점

  • raw AI의 4대 실패점을 구조적으로 봉합
  • 효과를 6개 메트릭으로 정량 추적
  • 효율=정확성 → 토큰 절감이 곧 드리프트 감소
  • 병렬 우선(Haiku Wave)으로 처리량 확보
  • 모델 티어링으로 비용·정확도 동시 최적화
  • 폴더 인지 컨텍스트로 불필요 토큰 차단

단점 / 비용

  • 마이크로 작업엔 오버헤드 — 완화: Qutopia SIMPLE 예외(스펙 생략)
  • 학습 곡선 (PSE 규율 · 183+ 스킬)
  • 검증·감독의 토큰/시간 비용 — Verification Tax로 감시
  • 선택적 Codex 브리지의 구성 복잡성
  • 하네스 자체의 유지보수 부담

단점 항목은 명시 문서가 없어 트레이드오프에서 추론 — 각 완화책은 프레임워크에 실재.

근거: core/PHILOSOPHY.md (Acknowledged Exceptions) · 단점=추론
7 / 8
솔직함이 신뢰를 만든다 — 단점을 먼저 인정하고 각각에 완화책을 붙이는 구성. 단점 목록은 근거: 추론(문서에 "단점" 절은 없음). 다만 완화책(Qutopia SIMPLE 예외, Verification Tax 메트릭)은 실재하는 사실. 예상 반론 "도입 비용이 크지 않나?" → "마이크로 작업은 SIMPLE로 우회하고, 검증 비용은 메트릭으로 상한을 본다"가 답.
결론

요약하면

  • 1. 모든 AI 작업은 결국 Query · Execute로 환원된다.
  • 2. raw AI는 스펙·구현규율·검증·감독 네 지점에서 무너진다.
  • 3. SIVS 루프가 그 네 구멍을 닫고, 하네스가 그걸 강제·계측한다.
