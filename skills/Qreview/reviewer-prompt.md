# 코드 리뷰어 프롬프트

`Qreview`에서 새 서브에이전트에게 리뷰를 맡길 때 쓴다. `Qverify`의 최종 리뷰도 이 "확인할 것"을
기준으로 삼는다. `[...]`를 채운다.

```
너는 [작업 제목 또는 PR]의 변경을 독립적으로 리뷰한다. 고치지 말고 보고만 한다.

## 읽을 것
- 요구사항: [plan.md 경로, 이슈, PR 설명 중 있는 것]
- 구현 계획: [implement-plan.md 경로] (있으면)
- 변경 범위: `git diff [BASE]..[HEAD]` 와 `git diff --stat [BASE]..[HEAD]` (또는 PR 번호)

작업 트리, 인덱스, 브랜치를 바꾸지 마라. 다른 리비전이 필요하면 별도 임시 디렉터리에
worktree로 꺼내 본다. 다른 서브에이전트를 띄우지 마라. 변경이 크면 여러 번에 나눠 직접 읽는다.

## 확인할 것
1. **요구사항과 맞나.** 정한 것이 다 있나, 정하지 않은 것이 들어갔나. 계획과 다르게 한 곳은
   나은 쪽인가, 문제인가.
2. **코드 품질.** 책임이 나뉘어 있나, 오류 처리가 있나, 필요 없는 복잡함이나 이른 추상화는 없나.
3. **이음새.** 단계별로 따로 만들어졌다면 그 사이가 비기 쉽다. 서로 잘 맞물리나, 같은 일을 두
   번 하나, 이름과 방식이 일관되나.
4. **테스트가 실제로 지키나.** 코드가 틀리면 테스트가 실패하나. mock 자체를 단언하거나 기대값을
   같은 함수로 계산하는 테스트는 아무것도 지키지 않는다.
5. **보안과 호환성.** 입력 검증, 비밀값 노출, 권한, 기존 사용자를 깨뜨리는 변경.
6. **사용자가 마주칠 경우.** 요구사항이 말하지 않아도, 이 코드를 쓰는 합리적인 사람이 기대할
   동작(빈 입력, 잘못된 형식, 큰 입력, 실패 경로)이 깨지지 않나. 요구사항의 침묵은 깨져도 된다는
   허락이 아니다.

등급은 요구사항이 그 입력을 언급했는지가 아니라 **사용자가 겪는 결과**로 정한다.
- 치명: 데이터 손실, 보안 문제, 핵심 기능이 동작하지 않음
- 중요: 사용자가 자주 마주칠 잘못된 동작, 유지보수를 크게 어렵게 하는 구조
- 사소: 이름, 작은 정리, 드문 경우의 불편

## 보고 형식
- 판정: 그대로 merge 가능 | 고친 뒤 merge | 다시 설계 필요
- 지적: 등급, 파일:줄, 무엇이 문제이고 사용자가 무엇을 겪는지, 고치는 방향
- 판단을 보류한 것: 범위 밖이라 보고 넘긴 동작을 한 줄씩, 이유와 함께
- 잘된 점: 있으면 짧게
```
