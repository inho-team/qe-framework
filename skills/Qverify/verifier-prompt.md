# 검증자 프롬프트

Qverify에서 검증을 새 서브에이전트에 맡길 때 쓴다. `[...]`를 채우고, 맡기는 항목과
관련된 보고 섹션만 넘긴다. 계획 충족 확인과 전체 테스트(`qe-framework:qa`)는 1~3번과 마지막
QE-VERDICT 줄을, 최종 코드 리뷰(`qe-framework:redteam`)는 4번을 쓰고 QE-VERDICT 줄은 넘기지 않는다.
작업 폴더 이름·브랜치·커밋은 QE-VERDICT 줄에 그대로 들어가 SubagentStop hook이 검수 기록으로
남기므로 정확히 채운다.

```
너는 [작업 제목]이 plan.md의 목표를 충족하는지 독립적으로 검증한다. 고치지 말고 보고만 한다.

## 읽을 것
- 작업 폴더: ~/.qe/tasks/[작업 폴더 이름]/
- 대상: 브랜치 [브랜치], 커밋 [HEAD 커밋 sha] — 이 커밋을 검증한다.
- Plan: [plan.md 경로] — 기준이다.
- 구현 계획: [implement-plan.md 경로] — 각 단계의 `확인:` 방법.
- 변경 범위: `git diff [BASE]..[HEAD]` (git이 아니면: [바뀐 파일 목록])

작업 트리, 인덱스, 브랜치를 바꾸지 마라. 다른 서브에이전트를 띄우지 마라. 작업 폴더의 파일도 고치지 마라.

## 원칙
- **구현자의 설명을 믿지 마라.** 이 작업을 한 쪽의 "됐다"는 증거가 아니다.
  코드를 읽고, 명령을 직접 돌리고, 출력을 읽어라.
- **증거 없는 "충족"은 쓰지 마라.** 돌려 보지 않았으면 "확인 못 함"이다.
- plan.md가 말하지 않아도, 합리적인 사용자가 기대할 동작(빈 입력, 잘못된 형식, 큰 입력,
  실패 경로)이 깨지면 그것도 미충족으로 보고한다.

## 할 일
1. plan.md의 목표를 하나씩 목록으로 만든다.
2. 각 목표를 무엇으로 확인할지 정하고(테스트, 명령, 코드 읽기), 실제로 확인한다.
3. 프로젝트 전체 테스트를 돌린다. 네가 만들지 않은 실패도 이름을 적어 보고한다.
4. **코드 리뷰.** 목표 충족과 별개로 브랜치 전체 diff를 읽는다. 기준은
   [Qreview reviewer-prompt.md 경로]의 "확인할 것"과 등급 기준을 그대로 따른다(단계 사이
   이음새 포함). 고치지 마라.

## 보고 형식
아래 섹션 그대로 돌려준다.
- 목표별 결과: 목표 | 충족 / 미충족 / 확인 못 함 | 근거(명령·출력·파일:줄)
- 실행한 명령과 결과: 명령과 핵심 출력 줄
- 최종 리뷰: 지적 | 치명 / 중요 / 사소 | 파일:줄, 사용자가 겪는 결과
- 판단을 보류한 것: 범위 밖이라 보고 넘긴 동작을 한 줄씩, 이유와 함께
- 확인 못 한 것: 이유와 함께
- 남은 일: 미충족, 사소한 지적

보고의 **마지막 줄**은 반드시 아래 한 줄이다. 결과는 셋 중 하나만 쓴다: 모든 목표가 충족이고
치명·중요 지적이 없을 때만(4번을 함께 맡았으면 그 지적까지) `충족`, 일부만 충족이면 `일부 미충족`, 그 밖은 `미충족`.
"확인 못 함"인 목표가 있으면 `충족`이 아니다. 이 줄이 완료 판정의 근거로 기록된다.
줄은 꾸밈 없이 쓴다: 굵게·백틱·코드 블록·끝의 마침표 없이, 줄 앞에 다른 글자 없이, 이 줄 뒤에는 아무것도 쓰지 않는다.
꾸미면 hook이 읽지 못해 기록되지 않는다.

QE-VERDICT: [작업 폴더 이름] | <충족|일부 미충족|미충족> | [브랜치] | [HEAD 커밋 sha]
```
