# Qverify — 검증

이 단계의 목적은 **"됐다"고 말하기 전에 spec 대비 증거로 확인하고, 그 증거를 남기는 것**이다.

확신은 증거가 아니다. "될 것이다", "아마", "보기엔 맞다"는 검증이 아니다.
이번에 직접 돌려 보지 않은 명령은 통과했다고 말할 수 없다.

## 누가 검증하나

상황을 보고 고른다.

- **메인에서** — 변경이 작고, 확인이 명령 몇 개로 끝날 때.
- **새 서브에이전트에게** ([verifier-prompt.md](verifier-prompt.md)) — 변경이 크거나,
  메인이 직접 많은 코드를 썼을 때. 자기가 쓴 코드를 자기가 채점하면 같은 맹점을 공유한다.
  깨끗한 컨텍스트의 검증자는 내 설명이 아니라 코드와 실행 결과만 본다.

고른 쪽과 이유를 verify.md 첫 섹션에 한 줄 쓴다. 서브에이전트가 "충족"이라고 보고해도
그대로 믿지 않는다. 핵심 근거 하나 이상은 내가 직접 확인한다. 서브에이전트에 맡길 때는
판단이 필요한 일이니 상위 모델을 지정한다(생략하면 세션 모델을 물려받는다).

## 확인 순서

모든 주장 앞에서:

1. **무엇이 이 주장을 증명하나?** 그 명령이나 방법을 정한다.
2. **돌린다.** 새로, 전체를. 예전 실행 결과는 증거가 아니다.
3. **읽는다.** 출력 전체, 종료 코드, 실패 수.
4. **출력이 주장을 뒷받침하나?** 아니면 실제 상태를 증거와 함께 말한다.
5. **그다음에야** 주장한다.

| 주장 | 필요한 것 | 충분하지 않은 것 |
|---|---|---|
| 테스트 통과 | 테스트 명령 출력: 실패 0 | 이전 실행, "통과할 것" |
| 빌드 성공 | 빌드 명령: 종료 코드 0 | 린터 통과 |
| 버그 수정 | 원래 증상을 재현한 테스트가 통과 | 코드를 바꿨으니 고쳐졌을 것 |
| 요구 충족 | spec 목표별 확인 목록 | 테스트가 통과했다 |
| 서브에이전트 완료 | diff와 확인 결과를 직접 봄 | 에이전트의 "성공" 보고 |

## spec 대비 확인

테스트 통과는 요구 충족이 아니다.

1. spec.md의 목표를 하나씩 목록으로 만든다. "기술적으로 돌아가도 실패인 것"도 포함한다.
2. 각 목표를 무엇으로 확인했는지, 결과가 어땠는지 적는다. 충족 / 미충족 / 확인 못 함.
3. plan.md의 "놓치기 쉬운 경우"가 실제로 덮였는지 본다.
4. 프로젝트 전체 테스트를 돌린다. 내가 만들지 않은 실패도 이름을 적는다.

## 최종 리뷰

spec 충족은 좋은 코드와 같지 않다. 검증 주체와 상관없이 **브랜치 전체**를 코드 리뷰한다.
단계마다 리뷰했어도 단계 사이의 이음새(맞물림, 중복, 일관성)는 아무도 안 봤을 수 있다.
리뷰 기준은 `Qreview`의 [reviewer-prompt.md](../Qreview/reviewer-prompt.md) 한 곳에 있다.
작은 변경이면 메인이 그 기준으로 diff를 한 번 읽는 것으로 충분하다. 서브에이전트에 맡기면
검증과 리뷰를 한 서브에이전트가 함께 한다: [verifier-prompt.md](verifier-prompt.md)의 리뷰
기준 자리에 그 파일의 **절대 경로**(이 스킬 폴더 옆 `Qreview` 폴더 안)를 채우거나, 그 파일의
"확인할 것"과 등급 기준을 그대로 붙여 넣는다. 상대 경로는 서브에이전트가 사용자 프로젝트에서
찾지 못한다.

지적은 `Qfeedback`으로 하나씩 맞는지 확인하고, **사용자가 겪는 결과**로 등급을 다시 매긴다(치명 / 중요 / 사소). 리뷰어가 "spec이
말하지 않아서" 낮게 매긴 것은 그 결과를 보고 다시 판단한다. 리뷰어가 판단을 보류한
항목은 내가 판단해 `판단:` 형식으로 남긴다.

**여기서는 고치지 않는다.** 지적을 등급과 함께 사용자에게 보여 준다. 사용자가 동의한
치명·중요 지적은 plan.md 끝에 `- [ ] 최종 리뷰 수정: <지적>` 단계로 추가한다. 그래야 세션이
끊겨도 남은 일로 다시 안내되고, `Qexecute`가 첫 미체크 단계부터 이어받는다. 이 수정은
**메인이 한 번에** 한다(실행 방식과 상관없이). 각각 재현 테스트가 먼저 실패하는 것을 본 뒤
고치고, 전체 테스트를 다시 돌린다. 중복·일관성처럼 재현 테스트를 만들 수 없는 지적은 그
이유를 verify.md에 쓴다. 고친 뒤에는 고친 부분을 다시 검증하고 verify.md를 갱신한다.
사용자가 고치지 않기로 한 지적과 사소한 것은 "남은 일"에 적는다.

치명·중요 지적이 미처리로 남아 있는 동안에는 "완료"라고 말하지 않는다.

## 실행 중 내린 판단 모으기

plan.md의 `판단:` 줄을 빠짐없이 verify.md "실행 중 내린 판단"과 최종 보고에 옮긴다.
"틀리면"까지 그대로. 내가 사용자 대신 내린 결정이 사용자에게 닿는 곳은 여기뿐이다.

## verify.md 쓰기

작업 폴더에 `verify.md`를 [verify-template.md](verify-template.md)로 쓴다. 읽는 사람은
"이게 정말 검증됐나?"를 묻는 미래의 사용자와, "무엇이 남았나?"를 묻는 다음 세션의 AI다.

- 실패와 미확인은 **그대로** 적는다. 좋게 포장한 검증 문서는 없는 것보다 나쁘다.
- 명령은 실제로 돌린 것을, 출력은 통과·실패를 보여 주는 핵심 줄을 적는다.
- 작은 일이면 몇 줄이면 된다.
- 머리의 `결과:` 줄에는 `충족`, `일부 미충족`, `미충족` 중 **하나만** 쓴다. 세션 시작 hook이
  이 줄을 읽어, 미충족인 작업을 다음 세션에 다시 알린다. 고친 뒤 다시 검증하면 이 줄도 갱신한다.

## 보고

사용자에게 짧게 보고한다: 결과(충족 / 일부 미충족 / 미충족), 핵심 근거, 최종 리뷰 지적,
실행 중 내린 판단, 확인 못 한 것, verify.md 경로.

- **미충족이 있으면** `Qexecute`로 돌아가 고칠지, 범위를 줄일지 사용자와 정한다.
  원인을 모르는 미충족이면 고치기 전에 `Qdebugging`으로 원인부터 찾는다.
  고친 뒤에는 다시 검증하고 verify.md를 갱신한다.
- **모두 충족이고 치명·중요 지적이 남지 않았으면** 그때 "완료"라고 말한다. git이면
  verify.md를 커밋한다. 다음은 `Qfinish`로 마무리한다(merge·PR·유지는 사용자가 고른다).

## 경고 신호

- "될 거야", "아마", "보기엔" 같은 말을 쓰려 할 때
- 확인 전에 만족을 표현하려 할 때 ("좋아요!", "완벽합니다!")
- 에이전트의 성공 보고를 그대로 옮기려 할 때
- "이번 한 번만", "부분 확인이면 충분해"라고 생각할 때

이 생각이 들면 멈추고 위 확인 순서로 돌아간다.
