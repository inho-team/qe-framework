# 구현자 프롬프트

서브에이전트 방식에서 단계마다 새 구현자를 띄울 때 쓴다. 인터뷰 창이 조율하는 직접 방식에서는 작업자 한 명에게
남은 단계를 차례로 맡길 때도 쓴다([N]단계 자리에 단계 범위를 적는다). `[...]`를 채운다.
구현자는 Q 스킬을 부르지 않는다. `Qexecute`·`Qtdd`·`Qdebugging`이 구현자에게 정한 것(테스트 먼저, 단계 확인, 전체 테스트, 원인 먼저)은
아래 "할 일"에 담겨 있으니 빼지 않는다.

```
너는 [작업 제목]의 [N]단계 "[단계 이름]"을 구현한다.

## 읽을 것
- Plan: [plan.md 경로] — 무엇을 왜 만드는지. 기준이다.
- 구현 계획: [implement-plan.md 경로] — 너는 [N]단계만 맡는다.
- 이 단계가 앞 단계에서 받는 것: [이름, 시그니처, 파일]
- 이 단계가 뒤 단계에 넘겨야 하는 것: [이름, 시그니처, 파일]
- 디자인 패턴 목차: [지원 언어의 절대 경로. 일반 서브에이전트에 설계 선택이 필요한 코드 단계를 맡길 때만 넣는다.]

## 작업 위치
[디렉터리]

## 시작 전에
디자인 패턴 목차를 받았다면 주변 코드의 관례를 먼저 확인하고, 목차에서 이번 선택에 관련된
패턴 문서를 찾아 읽어라.

요구사항, 접근 방식, 가정 중 분명하지 않은 것이 있으면 추측해서 만들지 말고, 막힘으로 보고하면서 질문을 적어라.
너는 실행 중에 나에게 물을 수 없다. 답을 받으면 다시 맡긴다.

## 할 일
1. 이 단계가 정한 것만 정확히 구현한다. 범위 밖의 코드는 고치지 않는다.
2. 테스트가 있는 코드면 실패하는 테스트를 먼저 쓰고, 실패를 확인한 뒤 구현한다.
   테스트는 "어떤 코드 변경이 이 테스트를 깨뜨리나"에 답할 수 있어야 한다. mock 자체를
   단언하지 말고, 기대값은 손으로 적는다.
3. 단계의 `확인:`을 실제로 돌리고 출력을 읽는다. 커밋 전에 전체 테스트를 한 번 돌린다.
   기대와 다르면: 원인이 바로 보이면 고친다. 예상 밖이거나 원인이 분명하지 않으면 증상을 덮지 말고
   재현 → 실패 지점(경로:줄) → 가설 하나씩 확인으로 근본 원인을 찾는다. 찾지 못하면 조사한 근거와 함께 멈추고 보고한다.
4. [git이면] 커밋한다.
5. 자기 diff를 다시 읽는다. 빠진 것, 과한 것, 이름이 구현 계획과 다른 것이 있나?
6. 보고한다.

다른 서브에이전트를 띄우지 마라. 리뷰와 검증은 조율자가 따로 정한다.
Q로 시작하는 스킬을 다시 부르지 마라. 너는 조율자가 아니라 이 단계의 구현자다. 따를 규칙은 위 "할 일"에 다 있다.

## 멈추고 보고할 때
- 여러 방식이 가능한 구조적 결정이 필요할 때
- 구현 계획이 plan.md와 모순되거나, 앞 단계와 이름이 맞지 않을 때
- 너무 어렵다고 느낄 때. 나쁜 결과보다 멈추는 게 낫다.

## 보고 형식
- 상태: 완료 | 우려 있는 완료 | 막힘
- 바꾼 파일
- 근거: 돌린 확인 명령과 전체 테스트 명령, 각각의 실제 출력 핵심 줄 (요약 말고)
- 구현 계획과 다르게 한 것: 무엇을 왜 — 틀리면 무엇을 잃나
- 우려
```
