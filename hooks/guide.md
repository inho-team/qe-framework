# QE — 이해 → 계획 → 실행 → 검증 → 마무리

이 프로젝트에는 QE가 설치되어 있다. 작업(버그, 기능, 리팩터링, 조사, 기획 등)은 아래 길 하나를 탄다.
길은 정해져 있지만, 각 단계 안에서 어떻게 할지는 네 판단에 맡긴다.
사용자의 지시(CLAUDE.md, AGENTS.md, 직접 요청)가 이 안내와 스킬보다 우선한다.

새 코딩 요청에 작업 이유(Why) 또는 완료 기준 중 하나라도 빠졌으면 첫 단계로 Skill 도구에서 `qe-framework:Qunderstand`를 호출한다. 구현 지시가 구체적이어도 사용 목적은 아직 모를 수 있다. 기존 대화와 저장소에서 확인한 사실은 다시 묻지 않는다.

1. **Qunderstand (이해)** — 요청의 의도와 완료 기준을 확인하고, 범위가 열려 있으면 가장 작은 유용한 접근을 함께 고른다.
2. **Qplan (계획)** — 이해한 것을 `plan.md`(사용자가 보는 계획)와 `implement-plan.md`(AI가 실행할 상세 계획)로 남긴다. 사용자가 승인해야 실행한다.
3. **Qexecute (실행)** — 계획대로 만들고 `implement-plan.md` 체크박스를 갱신한다.
4. **Qverify (검증)** — "됐다"고 말하기 전에 독립 검증자 서브에이전트(`qe-framework:qa`, 리뷰는 `qe-framework:redteam`)가 `plan.md`의 목표 대비 증거로 확인하고 `verify.md`에 남긴다. 충족 검수 기록이 있어야만 목표를 done으로 표시할 수 있다.
5. **Qfinish (마무리)** — 검증이 끝나면 문서를 프로젝트 `docs/qe/<목표>/`로 내보내고, merge·PR·유지 중 사용자가 고른 방식으로 닫는다.

코드 그래프가 있으면 `list_projects`에서 현재 작업 트리와 경로가 일치하는 인덱스를 골라 쓴다.
인덱스가 없고 그래프가 탐색 시간을 줄일 만하면 `index_repository`에 현재 작업 트리의 절대 경로(`repo_path`)를 넘긴다.
도구나 인덱스를 쓸 수 없으면 `Grep`·`Glob`·`Read`로 이어간다. 결론에 쓰는 결과는 현재 소스와 diff에서 확인한다.

길 옆의 보조 스킬:

- **Qdebugging (디버깅)** — 인터뷰로 기대 동작을 정한 버그는 새 작업자가 원인을 조사해 승인받을 계획에 담는다. 기대 동작이 처음부터 분명한 버그는 바로 조사한다.
- **Qtdd (테스트 먼저)** — 테스트를 쓰거나 고칠 때, 실행 안에서 테스트 먼저 구현할 때. 좋은 테스트의 조건.
- **Qreview (리뷰 요청)** — diff·브랜치·PR 리뷰를 요청받았을 때, merge 전. 새 서브에이전트가 독립적으로 본다.
- **Qfeedback (리뷰 받기)** — 리뷰 지적·PR 댓글을 받았을 때. 반영하기 전에 맞는지 확인하고, 틀리면 근거를 들어 반박한다.
- **Qreport (보고서)** — 분석·조사·디버깅 결과를 HTML·아티팩트로 달라고 할 때. 늘 같은 틀에 내용만 채운다.
- **Qskill (스킬 작성)** — 스킬을 만들거나 고칠 때, 스킬이 기대대로 불리지 않을 때.
- **Qboard (대시보드)** — 이 컴퓨터의 QE 목표·살아 있는 세션·주장과 증거가 어긋난 경고를 한 화면으로 보고 싶을 때.
- **Qcompact (넘기기)** — 세션을 넘겨야 할 때 `handoff.md`를 쓰고 사용자에게 `/compact`를 요청한다.
- **Qresume (이어받기)** — 아래에 미완료 작업이 보일 때 이어간다.

코드를 쓰거나 고칠 때는 `code-craft`를 따른다 — 문서 주석이 계약이고, 사설 주석은 쓰지 않는다.
`agent-conduct`는 QE 전문 에이전트가 싣는 공통 규칙이다(직접 부르지 않는다).

문서는 작업(목표)마다 `~/.qe/tasks/YYYY-MM-DD-<주제>/` 폴더 하나에 둔다. 프로젝트 밖에 두는 이유: worktree를 지워도
남고, 여러 세션이 같은 목표를 함께 하거나 넘겨받을 때 한곳을 본다. 사용자 본인과 다음 세션의 AI가 읽는다.
HTML 보고서(`report.html`, Qreport)도 같은 폴더에 둔다. 작업 없이 보고서만 있는 폴더(`status.json` 없음)는 작업 폴더가 아니다.
프로젝트의 `docs/contracts/`에는 지금 코드의 흐름을 순서도와 특이사항으로 정리한 계약이 쌓인다(원본은 코드).
단계별 일은 QE 전문 에이전트(`qe-framework:code-<언어>`, `qe-framework:redteam`,
`qe-framework:qa` 등)에 맡길 수 있다.

흐름: 폴더를 만들 때 `status.json`(`state: active`)부터 쓴다 → 어느 세션이든 같은 폴더를 갱신한다(세션·worktree
기록은 hook이 한다) → 체크박스가 다 차면 독립 검증자 검수(`QE-VERDICT` 줄을 hook이 기록) → 충족이면 `state: done`
→ Qfinish가 고른 마무리를 `done.finish`에 쓰고 검증한 브랜치의 `docs/qe/<목표>/`로 내보낸다. 사용자가 그만두면 `state: stopped`.
검수 없이 끝내려 하면 hook이 한 번 막고, 검수 기록 없이 done을 쓰면 거부한다. 우회하지 말고 Qverify로 간다.

코드 구현을 위임할 때는 언어에 맞는 `qe-framework:code-<언어>`를 쓸 수 있다.
코드 에이전트는 `code-craft`(코드와 문서 주석)와 `agent-conduct`(작업 범위와 보고)를
읽고, 설계 선택이 필요하면 자기 언어의 디자인 패턴 목차에서 관련 문서를 찾아 읽는다.
메인 세션도 접근을 비교하거나 직접 구현할 때 설계 선택이 필요하면 `Qunderstand`나
`Qexecute`의 언어별 목차를 연다. 코드 작성 중에는 `qe-framework:code-craft`에서도 찾을 수 있다.

이 작업을 인터뷰한 창은 인계와 승인 전달을 맡는다. 같은 창에서 `/compact`나 `/clear`를 해도 이 역할은 그대로이고, 세션 ID가 달라져도 새 작업자가 되지는 않는다. 재개 시 역할을 알 수 없으면 역할만 묻는다. 인터뷰를 진행한 창에서는 구현하지 않는다. 사용자가 의도를 확정하면 작업 폴더에 `intent.md`를 저장한다. 새 세션 또는 사용자가 선택한 서브에이전트가 이 파일을 읽고 계획을 세운 뒤 승인을 받아 실행한다.

인터뷰가 필요 없는 아주 작은 일(오타, 한 줄 수정)은 문서 없이 바로 하고 결과만 보고한다.
어느 쪽으로 판단했는지 사용자에게 한 줄로 말한다.

아래에 미완료 작업이 보이면 사용자에게 무엇이 남았는지 알리고 이어갈지 묻는다(`Qresume`).
사용자가 먼저 다른 일을 요청했으면 그 일을 막지 말고, 답 끝에 남은 작업이 있다고 한 줄만 알린다.
사용자가 그 작업을 그만두기로 하면, 확인을 받은 뒤 status.json `state`를 `stopped`로 쓴다.
"이전 위치(docs/qe)"로 안내된 작업은 v11 전 위치다. 이어가려면 먼저 `~/.qe/tasks/`로 옮긴다(`Qresume`).
